# WP11 consumer integration evidence

## Outcome

WP11 completes the core-owned consumer boundary without changing any consumer
repository or wrapping an `OntologyView`. The exact core implementation checkpoint is
`fe4be083fec4988a20def5f8e31c11da17a8dc40`; the adapter contract commit is
`75132daaf8f665b6f72dbbd7c9fcf30ef23e1eb7`.

The new `pyowl_core.adapters` package provides:

- the stable version-1 `CoreFeature` ledger around the existing public frozen
  `CoreCapabilities` identity;
- `AdapterRequirement` and exhaustive package/API/model/wire/feature/encoded-view
  negotiation, with every mismatch retained in one canonical diagnostic;
- path-free `ConsumerCacheKey` values binding the selected structural or logical
  fingerprint, the signature fingerprint, every independent core version, consumer
  API/compiler/compatibility schemas, and a caller-supplied semantic-options digest;
- metadata-only explicit plugin discovery that never calls `EntryPoint.load()`;
- a reusable provider probe, immutable before/after view observation, parser/resolver/
  wire/mmap/path call counters, exhaustive unsupported-feature reports, and a
  fail-closed handoff verifier; and
- instrumented path, bytes, stream, snapshot, provider, empty overlay, duplicate
  composite, core wire, and read-only mmap fixtures.

`CoreCapabilities` itself remains the exact class already exported by `pyowl_core`; no
wrapper or parallel equality domain was introduced. Existing views are returned by
identity. The adapter subpackage imports no consumer and performs no plugin discovery,
filesystem I/O, native probing, network access, or consumer import at import time.

## Core conformance matrix

The WP11 fixture contains typed declarations, an asserted hierarchy, a canonical
language-tagged annotation, and a deliberately unsupported data-property range. It proves:

- standalone acquisition and Python/native Functional parsing have equal public and
  consumer results;
- snapshot/provider/overlay/composite inputs add zero parser, resolver, wire, mmap, or
  path calls;
- direct, decoded, and mapped wire views have equal consumer result and cache-key bytes;
- import resolution occurs exactly once before consumer handoff;
- an OAEI source+target+bridge composite retains both member identities, and two bridge
  batches change only the bridge delta;
- composite in-process, materialized-reference, decoded-wire, and mmap results agree;
- unsupported/nonlogical constructor decisions must exactly match the complete counted
  report; and
- source tags `EN-gb` and `en-GB` share the canonical core literal `en-gb`, logical,
  structural, and semantic cache identity. Source spelling stays in the direct source
  map for pyELK's private compatibility key; decoded/mmap inputs use the documented
  canonical fallback. pyHermiT's key always consumes the canonical form.

## Deliberate boundaries and remaining release work

- Encoded structural view schemas remain empty. WP05 deliberately deferred a public bulk
  schema because it lacked measured benefit; requesting one now produces an exhaustive
  `MISSING_ENCODED_VIEW` report instead of a hidden scalar/path fallback.
- Syntax choice belongs to acquisition (`DocumentFormat` and `LoadOptions`), not an already
  loaded view. Negotiation therefore does not promise that a consumer can recover a source
  syntax after handoff.
- A forced native Functional parse still publishes the shared Python structural snapshot;
  the view backend label describes that public representation. Parser provenance and the
  focused native result prove native participation without exposing `_native`.
- These gates prove the shared input/cache/diagnostic boundary. They do not supersede each
  consumer's remaining release, large-data, reasoner-performance, or publication blockers.
  OAEI's existing large-ontology performance blocker and Exact's future package-version
  release decision remain consumer-owned.
